# Windows 临时高权限输入真机验收

本轮按操作者选择，先实现每次会话经本机 UAC 和独立授权的临时原生输入组件。最终目标仍是首次管理员安装后的服务方案；本轮没有安装服务、自动启动项或无人值守授权，也不发布新版安装包。

## 构建身份

- 交接基线：`87d050f2f3029140e1d5b5cd21ca2835d3ff611a`，源码版本 `0.1.13`。本分支 `codex/windows-elevated-input` 从前一诊断分支提交 `538836e3363e55ea04cd573fbc9f4855285c283f` 派生。
- Windows：Windows 11 x64，Electron `45.4.1`，本分支构建后以 `npm start` 启动，独立开发身份、显式局域网和临时输入开关。主进程、媒体采集和输入 utility process 保持 Medium；新原生组件实测 High。临时 DXGI 对照另外添加 `--nearlink-dxgi`，不是默认配置。
- Mac：操作者报告 `/Applications/NearLink.app`，`0.1.13`、Apple Silicon arm64、无额外参数。Mac 源码为交接基线且工作区干净，但已安装包的部分主进程脚本与该源码构建产物不一致，不能标记为基线提交构建。本轮 Windows 调试没有替换该 Mac 包。
- 原管理员策略文档中的“Windows 0.1.14 实测”没有可核对的构建对应关系，不沿用为本轮版本证据。

## 复现与证据修正

1. 原 Medium 输入路径能控制普通记事本。打开 High 的 WeGame 后，操作者最初报告卡住，切回普通窗口恢复。
2. 整个 Electron 提权是独立的失败对照：认证通过，WGC 初始化访问拒绝、未产生 answer 和视频帧，详见 [前一轮记录](windows-debugging-status.md)。临时组件方案不以整个 Electron 提权解决输入。
3. 接入临时 High 输入组件后，普通记事本收到文字；WeGame 和独立启动、令牌确认为 High 的 Notepad++ 起初仍被报告为卡住。此时组件持续 ready，协议回执正常，输入检查通过，SendInput 请求数与入队数一致。以上数据单独不能证明目标响应。
4. 要求同时观察 Windows 本机后，操作者明确确认：Windows 出现文字及鼠标移动，Mac 也能实时看到输入和点击结果。再次重连后确认实际操作有响应，但视频中的鼠标停留在最后一次普通 Notepad 操作的位置。因此不能继续把这一阶段的现象全部称为“高权限输入失效”；当前有实际输入成功证据，同时存在远端指针显示陈旧问题。
5. 消息循环修正是在第 4 步首次正向反馈前后加载的。首次正向反馈来自重启前，不能把输入恢复归因于该修正。它作为独立的消息等待缺陷修复保留。
6. 操作者进一步对照后报告：关闭调试者的 Computer Use 鼠标后，NearLink 指针恢复可见并能正常跟随。本轮指针异常据此归为调试环境中自动化鼠标的干扰，不作为已证实的 NearLink 采集缺陷。此前没有先隔离调试工具，导致多轮额外复测。随后撤销为该现象新增的控制端指针回退选项，停止 GUI 自动化，并恢复默认 Chromium 采集作最终回归。

主进程心跳和视频帧持续增长。High 组件与目标应用实测位于同一交互 Windows 会话、同一用户；组件与管理员编辑器均为完整提升令牌、无 UIAccess、非 AppContainer。普通权限只读探针在 High 窗口前台时可以成功获取、复制鼠标形状；未证明 Chromium 在其实际捕获上下文中收到正确的鼠标位置更新。

另做采集对照，操作者将画质设为手动 1080p 后，诊断明确记录 `captureBackend=dxgi`，帧持续增长且未回退；在未排除 Computer Use 时仍报告看不到正确指针。这次对照不支持将问题仅归于 Chromium，也不能把“打开 DXGI”当作修复。普通权限只读查询随后记录到 High 窗口前台时位置持续变化，不能声称普通权限无法读取高权限窗口上的鼠标位置。两个采集路径都受同一调试环境干扰的可能性应先排除；最终没有为它修改 DXGI 或 Chromium 采集代码。

操作者还报告：UU 能看到本轮安装／启动的 UAC 批准框，NearLink 看不到。这与普通桌面的 High 应用控制分开记录。Windows 默认把 UAC 提示放在安全桌面，当前临时组件明确排除该桌面，普通权限采集也没有覆盖它；不能以 High 应用输入成功宣称 UAC 可见或可操作。[微软 UAC 说明](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works)

## UU 的只读参考

本机运行的 UU GameViewer `4.44.0.3919` 中，UI 为 Medium；`GameViewerService` 为自动启动的 LocalSystem 服务，并有 Server／Healthd 工作进程。安装在 Program Files，检查的文件签名为有效 NetEase Authenticode，普通用户只有读取／执行权限。所检查 UI 与服务清单为 `asInvoker`、`uiAccess=false`。有限的驱动枚举未发现同名驱动，但这不是“没有驱动”的证明。

这些观察支持将安装、长期授权和桌面工作进程分离的架构方向，不能说明 UU 的私有输入 API、IPC 或安全桌面捕获机制。没有复制或使用其二进制、身份和协议，没有修改其服务。后续正式服务需要分别验收普通／High 应用、UAC 安全桌面提示的可见性、允许的交互范围及恢复；不能把临时输入 exe 直接改成 Session 0 服务而假设它可操作交互桌面。

## 本轮实现

输入仍通过隐藏 host 页面、专用 MessagePort、独立 utility process 和 InputState。显式开启开发选项时，最后的系统输入经本机命名管道交给 High 原生组件；它与普通输入复用鼠标手势和按键实现。媒体、配对、TLS、文件与剪贴板不进入该组件。

- 组件安装在 Program Files 下的专用受保护目录，按 SHA-256 分目录，拒绝重解析和普通用户可写的父目录／文件；启动前持有镜像读取句柄并复核摘要。使用静态 C/C++ runtime 和 System32 依赖搜索范围。该临时产物没有发行签名，摘要校验不能替代生产签名信任。
- UAC 后的独立 High 授权框展示当前对端指纹，由本机核对。授权范围明确为当前用户普通桌面的普通及管理员应用，绑定配对身份、NearLink 会话和认证连接代次，不采用未验收原型的单窗口授权模型。
- 管道无网络监听、拒绝远程客户端，使用随机名称、一次性 nonce、显式 ACL 和双向进程检查；核对用户、Windows 会话、进程创建时间及 OS 链接令牌。客户端采用 identification SQOS，避免让 Medium 服务端模拟 High 客户端。
- 有界二进制白名单协议，校验长度、严格连续序号、授权、按键文本上限、坐标范围和滚轮数值。组件只处理输入和授权生命周期，不提供任意命令、脚本、文件、剪贴板或提权执行接口。
- 4 秒输入租约；会话／连接撤销、锁屏、非 Default 桌面、显示布局变化、父进程退出和断管道停止新输入并释放本组件持有的状态。安全桌面上不切换桌面或注入，等待允许清理的桌面。未确认清理时禁止直接回落。
- 异步等待本机授权，期间处理撤权和断线，拒绝输入且不事后重放。媒体采集等待本机授权结束，避免 UAC 安全桌面期间启动采集。
- 修复 overlapped I/O 超时取消与完成竞争：完成先于取消时保留实际读到的数据，避免吞包后序号错误。创建过授权窗口的线程使用消息感知等待，持续处理自己的 Windows 消息。[微软等待与窗口说明](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-windows-in-threads)

生产包拒绝通过环境变量启用临时模式，打包排除临时 exe。原管理员授权策略、信任模型及隔离夹具继续受现有构建保护，不将它们的模拟测试计为本轮原生输入验收。

## 本机运行

在仓库的 x64 Native Tools 命令行：

```bat
npm ci
npm run native
npm run native:input-helper
npm run build
powershell.exe -NoProfile -File scripts\install-development-input-helper.ps1
set "NEARLINK_USER_DATA=%LOCALAPPDATA%\NearLink-Dev"
set "NEARLINK_DEV_LAN=1"
set "NEARLINK_DEV_ADMIN_INPUT=1"
npm start
```

安装脚本需要正常的本机 UAC。每次活动远控会话还需组件启动 UAC 及指纹授权；取消后不授予 High 输入。先完全退出之前的开发／安装实例，按独立开发身份配对。修改原生模块后重编译并退出旧输入进程；修改组件后重新安装对应摘要。`work/development-input-helper.json` 仅在本机使用，不提交。

验收应区分文字实际出现、窗口／控件实际响应、按钮松手、滚轮、视频继续刷新和指针位置。普通窗口、至少两个 High 目标、普通托盘及隐藏图标面板分别测试；再测断线撤销、父进程退出、授权取消和安全桌面边界。SendInput 返回值不代替这些观察。

## 验证与未解决项

- 生产构建通过，现有管理员原型构建保护未解除。
- 单元／回环网络测试 `109/112`，仍是前一轮三项 Windows 失败：两项符号链接 `EPERM`，一项安装超时后目录清理 `EBUSY`。
- 真实 Electron utility process／MessagePort 测试 `2/2`：主线程阻塞下独立松键，以及等待异步批准期间撤权和拒绝旧会话。native 适配器为合成记录器，不注入系统输入。
- MSVC 协议测试通过：非法参数／重放拒绝、512 次真实本机管道往返、短超时取消竞争，以及管道等待读取期间仍能响应窗口消息。该测试不注入键鼠。
- 父进程句柄监视探针通过；会话重连及重启后只观察到当前授权组件，没有安装服务或监听端口。
- 曾对本机指针回退做隔离界面检查；发现 Computer Use 干扰后已撤销该界面变更，最终不需要 Mac 更新才能恢复正常指针。合成截图和探针仍仅留在本机忽略目录。

当前已取得 High 窗口实际响应以及关闭 Computer Use 后指针正常的操作者反馈，默认采集下的最终滚轮、拖动释放、托盘双击及异常撤销矩阵仍在收尾。UAC 安全桌面不可见和整应用 High 的 WGC 零帧分别未解决。正式服务、签名安装／更新、无人值守信任策略及长期稳定性也未完成，不能据此发布生产管理员控制功能。
