# 安装式桌面服务预发布联调

候选版本 `0.1.16`，分支 `codex/windows-desktop-service`，叠在临时输入组件分支之上。`0.1.15` / `960a491` 已发布为预发布版，但实测发现服务认证、采集转发和输入问题，不能转正该产物。下面区分发布基线与 Windows 本地修正构建的验收。

## 结构及授权

首次在 Windows 托盘选择“安装无人值守服务…”，本机 UAC 后核对批准设备指纹及普通／安全桌面范围。服务与客户端复制到 Program Files 的摘要目录，目录与文件归 Administrators 所有，普通用户只读／执行。服务以 LocalSystem 自动启动在 Session 0；它用当前已登录用户的令牌，启动受保护副本中的普通权限 Electron。配对与身份继续使用原用户目录，服务不持有设备私钥。

服务只接受其启动的客户端的输入 utility process，核对实际镜像、摘要、所有者、ACL、Windows 用户和控制台会话；本机管道拒绝远程客户端，并核对服务端身份。不能用工作区中的 Electron 冒充受保护客户端。

首次安装批准的对端指纹写入受保护策略。设备指纹沿用 `identity-crypto.ts` 的 SHA-256(DER SubjectPublicKeyInfo)，不是整张证书的摘要。每次会话使用随机挑战；Mac 只为当前真实控制端会话签名，绑定主机、会话、对端、连接代次、Windows 会话及观看／控制范围。服务独立验证安装时批准的公钥指纹与 P-256 签名。重放、旧会话和观看授权升级为控制均拒绝。断线释放输入、退出会话工作进程；重连重新证明设备身份，不重复 UAC 或本机授权框。

服务为当前交互会话启动原生 LocalSystem 桌面工作进程。它只接受服务的私有管道，不开放网络或任意执行／文件接口。输入与采集分线程；采集使用当前输入桌面上的 GDI readback，经只读共享内存送到普通权限媒体工作进程及 WebRTC。安全桌面不能沿用 Medium WGC；默认桌面、UAC／Winlogon 切换时重建捕获线程、改变桌面代次，拒绝旧代次输入。共享映射只允许 System 写入，帧大小有上限，读取检查代次、时效和完整性。

服务使用 4 秒租约、父进程监视及工作进程 job。未确认按键清理时禁止继续授权。客户端关闭、网络会话撤销及服务退出不保留上次输入授权。服务自动重新启动用户客户端，停止整个后台程序应在 Windows 服务管理器停止／禁用 `NearLinkDesktopService`。

操作者确认本轮先验收登录后的重连、UAC 和锁屏。当前架构要求已有登录用户令牌及用户身份目录，“重启后尚未登录”的网络入口不计为已实现。受保护媒体或 Windows 的安全注意序列也不能由普通 SendInput 的成功回执推定已支持。

## 当前验证

- Windows x64 输入、捕获模块及服务 MSVC 编译通过；TypeScript／生产构建通过。
- Node P-256 设备证明 → Windows CNG 验证通过，篡改、错误指纹及错误上下文拒绝。
- 真实 utility process／MessagePort `4/4`：独立松键、待批准时撤权、安装式服务重连证明／观看租约与输入分离，以及服务帧／DXGI 帧分别读取。native 适配器为合成记录器；服务拒签与原生验签失败也会阻止采集启动。
- 单元／回环网络最新 `111/113`，剩余两项本机符号链接 EPERM。安装辅助进程 kill 后不等 close 导致的 EBUSY 已修复，对应 6 项专项和全量中的该用例通过；未改变系统安全设置或跳过符号链接用例。
- 首次实际安装已完成：SCM 服务为自动启动 LocalSystem／Session 0；受保护客户端自动启动于交互用户会话。未使用 Computer Use。
- 首次服务更新核实了带引号的 SCM 镜像路径及旧客户端退出／新客户端启动。Medium 客户端用 SCM 注册、运行账户和管道 PID／Session 0 验证服务，不要求读取 System 进程令牌。相同设备范围的更新沿用安装批准，重连不应触发安装程序。
- 第一轮独立 Windows CI 的 `113/113`、真实输入进程 `3/3` 及精确 NSIS 安装报告全部通过；后续 SCM 和桌面代次修正另行重建同提交的产物，不混用旧报告。桌面代次本机原生测试覆盖输入先观察到切换、重复观察不重复推进、布局撤销和并发观察。
- Mac 实际通过软件内更新到 `0.1.15` / `960a491`，Mac 两架构构建、113 项测试与更新清单签名核验完成。Windows 为该提交加本轮修正的本地构建，不能标作已发布的 `0.1.15` 二进制。
- Windows 修正构建已实测普通桌面输入／拖动、管理员 Notepad++、WeGame、滚轮、普通／隐藏托盘双击、UAC 显示及取消后返回、两次免本机确认重连、锁屏解锁。另在无活动远控会话时锁定，再从 Mac 新建连接、解锁并明确断开，用户确认一切正常且无需本机批准。服务视频实测持续 1920×1080、约 30fps。断开后记录 service-stopped，交互会话桌面工作进程为 0，LocalSystem 服务继续运行。
- 隐藏窗口真实 WebRTC 回归通过：主机可靠通道发送桌面代次、控制端输入带回该代次，并覆盖原有输入反馈、按键释放和界面交互。Windows 测试夹具修正文件 URL、退出清理和隐藏窗口不推进 CSS 过渡的问题；未更改产品动画。合成帧／回环延迟不代表真机跨设备延迟。
- 系统音频、安全注意序列、重启未登录、多显示器、受保护媒体、实际延迟和长期稳定性未计为验收通过。

## 0.1.15 双端复现与修正证据

控制端使用已安装的 Mac 0.1.15，Windows 使用服务保护副本。全程不使用 Computer Use 鼠标。依次从 Mac 连接、操作普通编辑器，再操作管理员窗口，触发真正的 UAC，最后锁屏和重连。

| 阶段 | 复现与定位 | 修正 |
| --- | --- | --- |
| 服务证明 | Mac 返回会话不匹配；本机调试安装引导的主机摘要等于整证书摘要，却不等于项目 SPKI 指纹。原生服务验签与旧合成夹具也错误地使用整证书摘要 | 调试引导改正；安装入口用真实证书重新计算并核对 SPKI 指纹；CNG 验签重新编码 SPKI 再校验 pin；夹具调用现有项目指纹函数，并断言整证书摘要被拒绝 |
| 连接后黑屏 | 认证和媒体连接已建立，但采集／编码帧数为零；capture worker 的消息参数遮蔽启动配置，使服务模式错误调用普通 DXGI reader | 启动时固定后端选择；真实 worker 分别验证服务帧和普通 DXGI 帧 |
| 有画面但输入被拒绝 | 收到按钮按下／松开，原生全部拒绝；被控端只保存反馈通道的局部引用，代次通知使用的成员通道仍为空 | 保存实际接受的可靠通道，按帧代次通知控制端；真实 WebRTC 验证代次通知及输入带回该代次 |
| 输入到达系统但无响应 | 代次一致，事件到达原生状态机；SendInput 请求 1／排队 0／Win32 错误 5 | 输入线程以 GENERIC_ALL 打开已批准的当前桌面，再 SetThreadDesktop；不修改系统桌面 DACL。修正后请求 1／排队 1／错误 0，用户确认实际操作恢复 |

桌面句柄的访问权限与进程账户权限是两个检查点。参考 [Microsoft 桌面对象权限](https://learn.microsoft.com/en-us/windows/win32/winstation/desktop-security-and-access-rights) 及 [Sunshine 的桌面绑定实现](https://github.com/LizardByte/Sunshine/blob/master/src/platform/windows/misc.cpp)。这属于服务工作进程的新链路；原先“整个 Electron 提权后 Chromium 采集零帧”的独立问题没有据此宣称修复。

诊断仅记录固定阶段、桌面代次及原生请求／排队／错误码，不记录键盘内容、帧图像、证书、签名或共享映射名称。内部服务线协议升级为 v2，保护副本中的客户端与服务须同次更新；Mac 设备证明的域与协议保持兼容。

## 构建、预发布与 Mac 更新

在 x64 Native Tools 命令行构建 Windows：

```bat
npm ci
npm run package:win
```

预发布只由原有更新私钥签名；私钥留在 Mac 发布环境。`0.1.14` 与 `0.1.15` 已存在，不能覆盖。GitHub 工作流在独立 Windows runner 构建本次具体提交，实际运行 NSIS、验证打包后的版本和原生模块，并输出与安装包 SHA-256 对应的报告；这不覆盖真实 UAC。

Mac 发布环境同步本分支的具体提交并保持工作区干净，运行：

```sh
npm ci
npm test
npm run package:mac
```

从同一提交的 Windows 工作流下载 `Windows-prerelease` 产物，将 Windows exe 放入 `outputs/installers`，报告放入 `outputs`。检查两端产物归属，使用 Mac 本机既有更新私钥执行 `npm run release:manifest`（从本版本文档生成说明和完整 `SHA256SUMS.txt`），再通过 `npm run release:publish` 仅发布 prerelease。工具检查两端报告、摘要、签名清单与实际提交，并将 release tag 固定到该提交，不能默认指向 main。默认稳定 Latest 不改变。待双端验收符合预期再按原流程转正，不能把草稿或不匹配的安装报告计为通过。

Mac 用户在现有应用“设置 → 软件更新 → 更新源设置”中填写该预发布的版本清单地址，然后使用“检查更新 → 下载 → 安装并重新打开”。发布完成前不提供尚不存在的下载地址。预发布必须保留既有身份与配对数据，私钥和原始日志均不上传。
