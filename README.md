# 近控 NearLink

局域网远程桌面测试版 0.1.13。Windows 11 x64、macOS 14.2+（Apple Silicon / Intel）。

首页左侧选择设备，点击右侧桌面预览打开独立全屏远控窗口；顶部工具栏自动收起。文件传输是独立的本机／对端双栏窗口。窗口关闭到后台，托盘菜单的“完全退出”才停止整个程序。

## 当前交付状态

实现了设备发现、双端指纹配对、公钥固定身份、TLS 信令及文件通道、WebRTC 画面／系统音频、原生键鼠、文字／PNG 剪贴板、文件及文件夹双向传输、断线重连和性能诊断。

4K 是采集／传输上限：1080p 源保持 1080p，4K 源保持 4K，更大的源按比例缩小；不会放大较低分辨率源。质量菜单的 4K 是上限而非强制输出尺寸。默认目标 60fps，低延迟自适应依次调整码率、分辨率与帧率。

早期本机桌面测试见 `outputs/local-validation.json`。0.1.4 新增只监听回环地址、不广播到局域网的隐藏实例回归，使用动态合成视频和静音音轨，覆盖生产 Runtime、TLS、IPC 和 WebRTC；这不等于 Windows 真机采集或两台物理电脑验收。**4K60、120fps、8 小时稳定性、Windows 实机与跨系统四方向尚未认证。** 120fps 尚未通过实测，因此普通设置中暂不开放。原生视频后端替换（ScreenCaptureKit/VideoToolbox、DXGI/MF/libwebrtc）尚未实施；须先在合格 4K 硬件上判断当前 Chromium 链路是否未达标，再进入该阶段。

## 安装与使用

安装包在 `outputs/installers/`。M 系列 Mac 使用 `mac-arm64`，Intel Mac 使用 `mac-x64`，Windows 使用 `win-x64.exe`。安装包是小范围测试包：Mac 使用本地 ad-hoc 签名，未做 Apple 公证；Windows 未做发布者签名。

1. 两台电脑处于互通的同一局域网，分别打开软件。
2. 在将被控制的 Mac 的设置页允许屏幕录制、辅助功能；系统声音首次连接时单独请求权限。系统要求重启软件时，使用“完全退出”后重开。
3. 在附近设备中选择对端，点击预览配对。若发现失败，使用对端设置页的 `IPv4:端口` 添加设备。
4. 核对两端显示的两组完整指纹，并分别确认。配对会授予远控、剪贴板和当前用户权限范围内的文件访问。
5. 点击桌面预览进入独立全屏远控。鼠标移到顶部中间显示工具栏，可以切换显示器、文件、画质、声音和诊断。
6. 文件窗口选中左侧项目后上传，选中右侧项目后下载。双击进入文件夹；支持 Ctrl/Command 多选，地址栏可直接输入路径。重名文件／根文件夹自动改名，符号链接不跟随。

关闭首页或远控窗口会隐藏并保留会话。托盘可恢复首页、恢复全屏远控或断开会话。“退出全屏”不结束连接。“断开”只结束远控；文件任务由独立队列管理。“完全退出”取消剩余任务、关闭服务并结束进程。

Windows 普通权限进程不能控制更高完整性等级的窗口或安全桌面。锁屏时暂停远控输入和剪贴板。首版不提供开机登录前控制、系统服务、远程解锁、手机端或跨互联网连接。

## 开发与验证

需要 Node.js 22.12+；已锁定 Electron 45.4.1。

```sh
npm ci
node node_modules/electron/install.js  # npm 禁止安装脚本时，显式安装官方运行时
npm run native                      # Mac 需要 Xcode Command Line Tools
npm run dev
```

Windows 编译原生模块需在 Visual Studio C++ Build Tools 的 x64 Native Tools 命令提示符中运行 `npm run native`。Git 仓库只提供源码，原生模块和 Windows 更新启动器需在本机编译；完整步骤见 [Windows 与 Mac 联合调试](docs/cross-platform-debugging.md)。

```sh
npm test
npm run build
npm run test:e2e   # 真实启动两个隔离实例，配对确认仅在测试进程中自动接受
npm run package:mac
npm run package:win
npm run package:source
```

`test:e2e` 需要可用桌面会话和系统远控权限。测试不会修改系统权限以绕过授权。Browser 插件未提供，因此使用 Playwright Electron 进行窗口、交互、截图和页面错误验证。系统声音轨道建立不等于已完成真实听感验收；请使用两台真实设备验证声音及剪贴板。

## 性能验收

远控工具栏 → 性能诊断可查看实际分辨率、采集／编码／呈现帧率、网络 RTT、编码／解码耗时、丢包和卡顿。RTT 不代表完整操作响应延迟。

“打开对端性能测试画面”会在被控电脑打开动态画面。“测量操作响应”实际通过原生输入注入点击，检查对应编号标记首次出现在接收视频帧的时间；没有测试标记时会停止发送测试点击。此测试仍需高帧率录像交叉验证实际显示器扫描呈现时间。导出记录包含两端会话、显示器参数、本机 CPU/GPU 与测量样本，不包含身份私钥、剪贴板正文或文件内容。

基准：合格 4K60 编解码硬件和显示器、千兆有线局域网 RTT≤5ms，动态测试 10 分钟平均呈现≥57fps；操作响应 P50≤80ms、P95≤150ms。多屏和 Wi-Fi 测试应分别覆盖各显示器，记录网络频段、实际 RTT 和接收显示器刷新率。Wi-Fi 的结果单列，不代替有线基准。

8 小时持续运行应包含至少 2 小时 4K60 动态画面，同时检查断网恢复、切屏、显示器拔插、睡眠唤醒、文件传输和内存趋势。当前源码提供测量与导出工具，未把尚未运行的测试标记为通过。

## 实现边界

- 主进程持有配对身份、会话、文件队列和托盘；隐藏的媒体页面持有被控端采集，远控窗口保留控制端连接。首页生命周期不持有这些资源。
- 私钥由系统安全存储加密；首次人工核对完整 SPKI SHA-256 指纹，后续公钥固定。未配对连接只能协商配对，其他操作需要认证，桌面预览也受保护。
- 键鼠经独立 WebRTC 数据通道传输；鼠标移动合并并丢弃过期包，可靠通道用于按键／按钮释放。文件分块流式处理，根据实时指标限速；接收端校验 SHA-256 后发布最终文件。
- macOS 音频来自 Core Audio Tap，通过有界 PCM 环形缓冲和 AudioWorklet 进入 WebRTC；Windows 使用回环音频。
- 协议和 MediaEngine 接口为后续媒体后端、手机控制与跨网络信令保留分层；首版没有云服务或账号。

## 0.1.1 输入、画质和更新

远控窗口采用系统窗口边框，退出全屏后可拖动和缩放。视频点击时阻止浏览器把焦点从隐藏输入框移走；窗口恢复和关闭面板后恢复输入焦点。远控画面中隐藏本机指针，工具栏和失焦时恢复。画质菜单提供原生清晰与设备像素显示；WebRTC 的网络 jitter 与播放缓冲 delay 分开记录。

更新通过 `https://github.com/tr1ee/NearLink/releases/latest/download/nearlink-update.json` 获取发布清单。清单使用 Ed25519 签名，安装包使用 SHA-256 和长度双重校验。发布公钥随应用提供；私钥只保存在本地 `.release/update-private.pem`，不进入源码归档、Git 或公开 Releases，必须单独备份。

`npm run release:manifest` 在三个架构的更新包齐备后生成签名清单；`npm run release:publish` 通过已登录的 GitHub CLI 发布安装包、清单、校验值和说明。该命令不会上传源码。发布前先递增 package.json/package-lock.json 版本，重新构建和验证安装包，并更新发布说明。不要重新生成发布密钥，否则已有客户端将拒绝更新。

测试版本默认发布为 GitHub 预发布，稳定更新源继续指向原有 Latest。验收结束并得到用户明确确认后，使用 `npm run release:publish -- --stable` 将同一标签下、两端安装包均已齐备并核验的预发布转为 Latest。沿用该标签即可完成正式发布。

测试版通过发布验证后，直接发布到 GitHub Releases 并设为 Latest，供软件内更新。发布后用生产下载器验证 Latest 清单及各平台安装包校验值。

首次从 0.1.0 升级仍需手动安装一次。其后从设置页下载并确认安装，安装会停止当前会话。Mac 使用签名校验和带备份的目录替换，随后重新打开；Windows 使用 NSIS 静默覆盖安装。Mac 的 ad-hoc 签名不能替代 Developer ID 与公证，系统仍可能要求再次确认权限。

更新测试使用临时 TLS 证书和发布密钥，仅在隔离测试进程中注入，不提供生产覆盖入口。`node scripts/test-update-install-mac.mjs` 使用无界面的微型应用在 work/ 中测试真实 Mac 替换、备份、重新启动及坏包拒绝；不会改动已安装软件。Windows 安装替换需 Windows 真机验证。

## 0.1.2 升级后连接恢复

默认监听51820，实际端口写入用户数据目录的transport.json并在重启后复用。端口占用时保存新的可用端口。发现处理up、srv-update和txt-update，每次进程启动使用独立实例名；过期down和旧连接关闭不能覆盖新端点。已配对设备只有完成认证才显示在线，后台定期探测，连接失败时刷新发现并尝试更新地址。公钥固定规则保持不变。

`tests/network.test.ts`使用真实TLS/WSS验证端口变化、旧广播、双端同时重连及错误身份拒绝。`tests/network-restart.spec.ts`通过`--background`启动隐藏的隔离实例，验证单端重启、端口占用、身份保留及RPC恢复。指定该测试和updates.spec.ts可进行不占用前台键鼠的回归。`--background`仅隐藏首页，托盘仍可恢复。

## 0.1.2 鼠标与交互延迟

鼠标发送脱离视频rAF：首包立即发，后续4ms合并最新位置，背压只保留最后一个位置。接收器只允许一个输入IPC在执行、一个最新移动及最多128个可靠命令；过载优先释放按键。点击及释放附带序号，丢弃迟到的旧移动，同时可靠命令不能因较新移动先到而被忽略。此协议扩展兼容旧版，新增输入通道探测需先通过能力消息确认。

视频与音频使用不同MSID同步组及独立播放流，避免音频缓冲增长强制拖慢视频。保持文字内容编码提示和原生分辨率；自动码率从预算65%起步，预算按源像素和帧率封顶，持续RTT增长或发送排队也触发降码率。诊断分开记录输入通道RTT、IPC/原生执行耗时、视频发送排队、接收缓冲和丢帧。缓冲目标不等于实际可保证延迟，参考[WebRTC规范](https://www.w3.org/TR/webrtc/#dom-rtcrtpreceiver-jitterbuffertarget)。

`tests/input.test.ts`覆盖发送与接收背压、序号乱序、按键释放、拥塞与源屏码率预算。`tests/input-latency.spec.ts`在两个隐藏页面中用生产MediaEngine传输1080p60动态canvas和静音音轨，真实RTCDataChannel输入触发模拟桌面标记，在接收video帧回调读取标记；不注入系统输入、不采集真实屏幕。该结果只验证媒体和输入调度，不能替代跨电脑实际操作延迟验收。

## 0.1.3 Windows 安装与后台生命周期

Windows 更新通过系统 PowerShell 的绝对路径启动独立辅助进程，工作目录位于用户更新目录；结构化 JSON 请求避免路径和命令参数混淆。主程序等待匹配令牌的 ready 状态，辅助进程预检及安装包校验通过才退出。解析和进程启动错误写入 install-startup.log，执行阶段写入 install.log 和 install-result.json。NSIS 使用 --updated /S，并把未加引号的 /D=目录放在最后，这是NSIS对该参数的特殊要求。

安装后从目标 resources/app.asar 读取实际 package.json 版本，不能仅凭退出码0报成功；新程序初始化后写回启动确认。失败时保留错误，并在原程序仍存在时尝试恢复打开。tests/windows-install.test.ts验证启动握手、失败、超时及版本确认；scripts/test-update-install-win.mjs用真实PowerShell解析器和隔离ASAR回归成功、哈希失败、安装非零返回及版本未替换，安装进程命令由测试模拟，不能替代Windows NSIS/UAC实测。

Windows将普通关闭和完全退出区分：关闭立即隐藏，媒体与网络资源保留；未明确请求的 before-quit 被转为后台。托盘退出、设置退出、更新安装和系统会话结束仍允许真正退出。增加Windows遮挡后台参数，保留已有 backgroundThrottling:false。网络集成测试通过真实窗口close验证实例和RPC保持；Windows before-quit分支在Mac进程中模拟，仍需对应Win11真机确认。

受旧Windows更新器影响的0.1.1/0.1.2用户需手动覆盖安装0.1.3一次，不能用新下载包追溯替换已运行旧版的启动逻辑。无需卸载或删除配对。Mac0.1.2可以继续与Windows0.1.3连接，不要求同步更新。


## 0.1.4 后台恢复、设备列表与帧率

采集页和远控页使用独立 Electron session partition，与首页分配不同渲染进程。最小化、关闭到后台时继续禁用媒体节流；媒体进程崩溃或持续无响应时重载并重新协商，会话不依赖首页重新打开。初始化握手暂存有界信令，防止新页面未就绪时丢失 offer；失败消息带会话编号，过期失败不影响新会话。采集等待可立即取消且有超时，晚返回的流会释放，停止不会堵在采集队列后。自动重连仍由主进程调度，用户主动断开不重连。

视频采集显式请求最低／目标／最高帧率，动态调整时同步更新三者，避免出现 min60/max30 的冲突。使用 motion 内容提示，优先连续交互；保留原生尺寸上限和对齐后的自适应尺寸，不通过 JavaScript 搬运整帧。默认目标60fps，正常动态交互的最低验收要求为30fps，硬件、网络不足时仍需真实测量。静态重复帧不作为动态达标依据。诊断新增“目标／采集配置 fps”，低码率以 kbps 显示。

“我的设备”只显示已配对公钥身份，未配对设备在“全部设备”。mDNS PTR/SRV/TXT 响应刷新租约，过期未配对记录清除，旧实例的 goodbye 不清除新实例。未完成 hello 就断开的 TLS 连接不再写入“连接中”占位条目，已有配对和公钥校验保留。开发隔离配置禁用 mDNS 且只监听127.0.0.1，避免测试身份污染真实设备列表；正式打包应用仍发现局域网。

新增滚动日志 userData/logs/session.jsonl（约1MiB、另保留一份旧日志），记录后台窗口、媒体重载、网络认证和主进程调度间隔，不记录剪贴板正文或文件内容。诊断导出包括近期日志和媒体进程信息。

`tests/session-lifecycle.spec.ts` 使用两个真实隐藏实例及生产网络／媒体链路，模拟动态1080p60画面，验证卡住采集取消、两端首页和远控窗口最小化／关闭、采集与控制渲染进程实际强制终止后的恢复，以及恢复后持续呈现不低于30fps。强制故障后的编码预热允许短暂降帧，报告保留全部4秒测量窗口，不能把恢复瞬间剔除后宣称全程稳定。`tests/device-list.spec.ts` 用实际 Home 组件检查12个同名不同公钥身份的列表排布。测试模拟Windows平台分支，未执行Windows窗口管理器或真实Windows屏幕采集。

本轮需两端升级0.1.4以验证完整修复；0.1.3可使用应用内更新。Windows0.1.1/0.1.2更新器异常时需手动覆盖一次，无需卸载或重新配对。实际Windows动态帧率、Wi-Fi延迟、4K60和8小时稳定性尚未认证。


## 0.1.5 更新安装修复

Mac ENOTEMPTY已在真实Electron中复现：普通fs递归删除含app.asar的目录时残留归档，original-fs可正确清理。更新文件使用original-fs真实磁盘接口，不切换全局process.noAsar，参见[Electron ASAR说明](https://www.electronjs.org/docs/latest/tutorial/asar-archives#treating-an-asar-archive-as-a-normal-file)。每次安装创建独立staging.noindex/install-*目录，不再先删除共享unpacked；失败仅清理本次准备目录，重试不受旧解包影响。确认对话框前就锁定安装流程，重复点击不能并行解包或启动多个安装辅助进程。

新版成功启动后清理本更新目录中当前及旧版NearLink ZIP/EXE/临时下载文件、旧unpacked和本次解包目录；更高版本下载、配置、日志和失败结果保留。Mac旧应用备份通过相同真实文件系统接口清理；Windows安装助手仅在真实安装版本与启动确认均通过后删除本次安装包，文件占用时重试，失败缓存保留。这里只处理应用自己的updates目录，不删除用户Downloads中的手动安装包。

## 0.1.6 Windows输入独立于窗口消息循环

Windows0.1.5曾出现远程点击标题栏最小化/关闭按钮后主线程长时间停顿及连接断开的故障。这与Windows非客户区鼠标跟踪循环等待抬起、而原来的抬起事件还要经同一Electron主线程处理的相互等待机制吻合。原先只模拟窗口hide/close，没有覆盖这条实际远程输入路径。

Windows现在用utilityProcess独立加载原生输入模块，通过MessagePort与被控采集页预加载直连。主进程仅分配和撤销会话权限、提供选定显示器的物理边界，不再注入Windows键鼠。按下、抬起、组合键和文字仍走原来的加密RTC可靠通道/有界队列，到达被控端后绕过窗口主线程；Mac被控仍使用原路径。该通道仅交给采集页面，工作进程验证当前会话、只观看/锁屏/断线权限、输入schema与序号，4秒失去心跳时释放并停止接受；通道关闭、会话停止和退出亦释放。

新增tests/input-worker.spec.ts使用实际生产preload、WindowsInputService及由ASAR解包入口启动的真实utilityProcess，故意让主线程同步等待模拟按钮抬起；独立输入仍执行按下/抬起并使等待结束。原生输入为记录事件的模拟适配器，不注入系统键鼠；不能据此宣称真实Windows WM_NCLBUTTONDOWN已通过。单位测试覆盖撤权、过期会话、负屏幕物理坐标、乱序抬起和心跳失效释放。诊断/设备信息新增输入进程pid与就绪状态，不记录输入正文。

本轮优先升级Windows0.1.6即可，Mac0.1.5控制端与之兼容，无需卸载或重新配对。Windows0.1.5含更新安装握手，可应用内升级；如果应用内安装仍失败，需保留新生成的安装日志排查。Windows实际标题栏最小化/关闭、长拖拽与缩放、多屏DPI及高权限窗口仍需对应真机回归。Mac0.1.6安装包也提供，但不是这次Windows修复的依赖。此前4K60和长期稳定性的未认证状态保持。

实现依据：[Electron utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process)、[MessagePorts直连](https://www.electronjs.org/docs/latest/tutorial/message-ports)。

## 0.1.8 接收视频即时播放

0.1.7之后优先检查接收视频的播放等待。网络RTT和原生输入耗时较低时，视频缓冲仍可能增加操作反馈延迟。采集与呈现帧率需要用动态画面复测，不能把静态桌面的帧率直接当成采集上限。

- 启动时设置Chromium原生视频接收策略`WebRTC-ForcePlayoutDelay/min_ms:0,max_ms:0/`，收到可解码视频帧后尽快解码呈现。原有`jitterBufferTarget=0`/`playoutDelayHint=0`仅影响最低延迟，不能限制浏览器内部的自适应等待；不更改音频缓冲。视频在网络抖动时可能丢弃更多迟到帧，以交互及时性为先。此设置不能保证物理显示延迟为零。
- 仅调整码率时不再反复提交相同的屏幕采集约束，避免不必要的采集重配置。明确的编码过载直接降低分辨率以减轻像素负担；网络拥塞仍先降低码率，静态低帧率不触发编码过载降档。
- 诊断增加实际协商的视频编码格式、选中ICE通道的UDP/TCP与候选类型、缓冲目标和网络最低缓冲。网络RTT优先采用实际选中通道的当前值。滚动日志和导出记录包含这些信息及启动时的播放策略、Chromium版本。硬解后端未报告时继续显示未报告，不推断硬件状态。

实现依据：[WebRTC原生接收播放范围](https://webrtc.googlesource.com/src/+/refs/heads/main/video/rtp_video_stream_receiver2.cc)、[接收播放范围优先级](https://webrtc.googlesource.com/src/+/refs/heads/main/video/video_receive_stream2.cc)、[WebRTC视频适配机制](https://webrtc.googlesource.com/src/+/91dbc17ae49f9fbf2071b5d60bf1b823973c4a4f/video/g3doc/adaptation.md)。播放策略依赖内部field trial，当前固定Electron45.4.1/Chromium156.0.8078.100，并已确认所带二进制含此实现；升级Electron必须重跑行为测试，不能只检查命令行字符串。

验证使用生产MediaEngine、真实RTCDataChannel与H264/UDP视频、合成1080p60源。刻意把接收器的API缓冲目标设为160ms：关闭新策略的对照实际平均缓冲约139.3ms，开启后约0.37ms（137帧）；目标恢复为0时，正常合成操作反馈中位数约33.5ms、P95约50.4ms。码率从9.1降至6.825Mbps时采集约束调用次数保持1次。该实验验证播放调度与码率配置，未复现用户Windows屏幕采集、Wi-Fi抖动或物理显示扫描，不能直接宣称已解决真机160ms延迟，也未新增4K60或8小时认证。

0.1.8需优先更新作为控制端的Mac并完全退出后重开，因为主要修复在接收端。建议Windows也更新，以使用采集/自适应改进。保持0.1.7协议兼容，无需删除配置或重新配对。升级后先用同一屏幕、相同画质复测视频缓冲和采集到呈现；若缓冲仍高，请导出记录以检查原生策略是否实际生效。

最终验证：生产构建、58项单元/回环网络测试、4项隐藏Electron回归通过。后者覆盖160ms缓冲对照、可靠输入/键盘与诊断面板开关、主线程不调度时输入进程仍释放鼠标、60次预览复用、两端隐藏窗口及媒体进程崩溃恢复。Browser插件未提供，界面测试使用Playwright Electron；截图和诊断样本留在本地，不随源码上传。这些结果不等于Windows用户环境已验收。

## 0.1.9 窗口比例和鼠标响应

退出全屏或切换远端显示器时，窗口内容区按被控屏幕比例调整。窗口优先按远端像素尺寸换算至本机显示器，超出可用区域时等比缩小。系统标题栏计入外框，默认适应窗口模式下完整显示画面。

支持 `pointerrawupdate` 的环境优先处理原始鼠标移动，普通指针事件作为兼容路径。现有移动合并、按钮坐标和可靠按键顺序仍适用。远控面板改用实体背景，避免在播放期间对视频持续计算模糊。音轨到达时单独启动音频，不重复装载视频流。

性能诊断新增平均采集帧间隔，便于用动态测试画面对比帧率。对照最小化操作时，将 Windows 自身的动画时长与画面传输耗时分开测量。Windows GPU 纹理采集暂不默认启用，Electron 上游有启用后显存持续增长的报告，见 [Electron #55180](https://github.com/electron/electron/issues/55180)。

## 远控性能对照

实测对照优先用 UU 远程，原生媒体实现参考 Parsec 和 Sunshine／Moonlight。对照时分别核对采集后端、实际编码格式、硬件编解码状态与直连通道，各软件的「帧延时」统计范围可能不同。Parsec 公开了 GPU 内采集到编码路径、硬解和帧调度，并区分采集、编解码和帧间隔。Moonlight 还单独记录解码后的等候与呈现时间。[Parsec 架构](https://support.parsec.app/hc/en-us/articles/32361354307348-Overview) · [Parsec 统计字段](https://support.parsec.app/hc/en-us/articles/32381603663636-Stream-Overlay-Stats-and-Logging) · [Moonlight 统计实现](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg.cpp)

对照使用相同的 Mac、Windows 显示器、网络、1080p 和两款软件都支持的帧率，每次只保留一条视频会话。用同一动态画面比较实际呈现帧率与卡顿。使用实体双屏的高帧率录像比较点击到第一帧变化，并分别记录最小化动画起始和结束在两屏上的偏移。NearLink 可先用「测量操作响应」获得 30 次样本的 P50/P95。

动态画面若仍主要在采集阶段降帧，首个原生实验应针对 Windows 的 DXGI 桌面复制与 GPU 内硬件编码。保留当前加密直连作为对照，分别测试 H.264 与 H.265。若瓶颈主要在 Mac 解码后到呈现，则比较 VideoToolbox 和 Metal 路径，以及帧队列与等待下一次刷新所占时间。[DXGI 桌面复制接口](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) · [Parsec 渲染与 VSync 选项](https://support.parsec.app/hc/en-us/articles/32381443626516-All-Advanced-Configuration-Options)

## 0.1.10 恢复远控键鼠和光标

Mac 重新激活应用时保留前台远控窗口的焦点，切换全屏后恢复远控渲染页的输入焦点。普通鼠标移动在原始事件缺失时仍会转发，命中同一次移动的事件只发送一次。控制端保留本机指针作为即时位置反馈。被控画面包含远端指针时，移动中可能短暂看到两个指针。重新选择远控或仅观看会重新协商，工具栏明确显示仅观看状态。

窗口比例沿用 0.1.9 的远端屏幕适配。诊断把本机接收到呈现分成最后一个视频包到提交画面、提交到预计显示两个区间，均为 Chromium 时间估计。最小化反馈应以点击到画面首次改变、再到窗口完全消失的时间评估。

合成 1080p 对照中，默认和禁用 Chromium WebRTC 平滑呈现时，模拟鼠标移动到画面变化的中位数约为 33.3 和 33.4ms。提交到预计显示中位数约为 24ms，默认沿用原有策略。真实 Mac 控制 Windows 的延迟仍以同机测试结果为准。
